# Project 1 proposal | 服务器持续高负载调查助手

**问题与用户。** 运维人员看到某台服务器 CPU 很高，需要先判断：是短暂尖峰，还是连续多个采样周期都很高？第一版帮助定位需要调查的服务器，展示起止时间、持续时间和读数；高负载本身不是故障诊断。

**数据。** 先用[明确标注的合成 CSV](../data/demo/cpu_synthetic.csv)演示单机与多机记录；没有真实遥测或事故标签。数据字段、时间口径与缺失处理见[数据说明](../docs/operational-data.md)。后续只有在来源、授权、采样方式清楚后才引入运营数据。

**方法。** 先实现无需 AI 的规则。为演示，连续三个相邻的五分钟区间 CPU 平均使用率均 ≥85% 就生成一个事件。85% 和 15 分钟是示例配置，不是行业标准。输出证据供人工判断。对真实数据应先检查基线、业务周期和误报成本。

**系统与部署。** 当前可在本地从 CSV 生成事件和趋势图。[架构图](../docs/architecture.md)标出未来网页与 AI 解释层；计划提供可公开访问的演示，仅展示可公开数据。已有 GPU 容量计算保留为独立功能，不依据 CPU 使用率推算 GPU 需求。

**验收。** 合成样例必须只标出预期服务器和区间；短尖峰和跨缺口的高读数不得合并告警。无密钥时仍可运行，输入无效时清楚报错。后续在固定案例上比较“只看规则”与“规则加 AI 解释”，记录定位正确性、无依据说法和调查用时；没有真实标签时不报告真实故障识别率。

**AI 与人工复核。** 未来 AI 只能解释已有事件或引用资料；没有支持证据时应说明未知。人工检查规则、核算边界样例、审查代码和失败案例后再发布。
